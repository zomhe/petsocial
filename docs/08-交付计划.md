# 研发排期、人员配置、测试、灰度、上线与回滚

## 1. 建议团队

| 角色 | 人数 | 主要职责 |
|---|---:|---|
| 产品经理 | 1 | PRD、流程、验收、运营协作 |
| UX/UI 设计 | 1 | 设计系统、原型、可用性测试 |
| 小程序前端 | 2 | 小程序、性能、微信能力 |
| 管理前端 | 1 | 运营后台、幼儿园工作台 |
| 后端 | 2～3 | 业务、支付、审核、通知、数据 |
| QA | 1～2 | 测试策略、自动化、发布验证 |
| 数据分析 | 0.5 | 埋点、口径、看板与对账 |
| DevOps/SRE | 0.5 | 环境、发布、监控、应急 |
| 内容安全/运营 | 1～2 | 审核、举报、社区冷启动 |
| 幼儿园业务负责人 | 1（业务侧） | 评估、容量、异常与售后规则 |
| 隐私/法务 | 按阶段投入 | 协议、隐私、支付与线下服务审查 |

若仅 1 名后端或无专职 QA，8～12 周不现实，应缩范围或延长工期，不能删除安全与支付质量保障。

## 2. 研发前置（第 0～2 周）

- 完成约 30 名犬主、物业与幼儿园访谈；
- 冻结试点社区、主体、认证方式、退款规则和严重事件联系人；
- 完成高保真原型并对 10～15 名目标用户做可用性测试；
- 完成隐私数据清单、威胁建模、状态机和接口评审；
- 配置小程序、支付、地图、内容安全、对象存储与各环境；
- 建立 DoR（可开发标准）和 DoD（完成标准）。

## 3. 10 周 MVP 研发计划

| 周 | 目标 | 主要交付 |
|---|---|---|
| 1 | 工程与身份底座 | 仓库、CI、环境、登录、协议、权限框架、审计框架 |
| 2 | 狗狗与社区 | 主人/多犬档案、字段分级、社区/邀请码、公共地点 |
| 3 | 内容社区 | 发布、媒体上传、列表详情、点赞评论、机器审核 |
| 4 | 关系与治理 | 关注、收藏、拉黑、举报、人工审核队列、处罚 |
| 5 | 附近与邀约一 | 模糊位置、附近列表、邀约创建/列表/报名 |
| 6 | 邀约二 | 审批、取消、提醒、快捷状态、完成、评价、异常 |
| 7 | 幼儿园一 | 门店/服务、档案授权、评估、容量、订单创建 |
| 8 | 幼儿园二 | 支付、签到、服务、日报、异常、接回、退款 |
| 9 | 联调与硬化 | 通知、后台补齐、埋点、性能、安全、容灾演练 |
| 10 | UAT 与发布候选 | 全量回归、数据对账、运营演练、RC、灰度审批 |

### 并行工作流

- 小程序：入驻 → 社区 → 邀约 → 幼儿园；
- 后端 A：身份/社区/内容/治理；
- 后端 B：邀约/通知；
- 后端 C：幼儿园/支付（若仅 2 人则 B、C 合并并调整排期）；
- 管理前端：第 2 周搭框架，第 3 周起按后端模块跟进；
- QA：第 1 周开始评审，第 3 周开始持续自动化，不在第 9 周才介入。

## 4. 里程碑与退出条件

### M1：核心社区可用（第 4 周末）

- 可完成登录、创建狗狗、加入社区、发帖互动；
- 审核、举报、拉黑和审计链路可用；
- 敏感字段越权测试通过。

### M2：遛狗闭环可用（第 6 周末）

- 从创建到完成评价全链路通过；
- 容量、时间、拉黑、状态机均后端强校验；
- 取消、爽约、争议和提醒有测试结果。

### M3：幼儿园闭环可用（第 8 周末）

- 评估前无法支付，容量无超卖；
- 支付、回调、退款幂等与对账通过；
- 日报、异常、接回访问权限通过。

### RC：灰度候选（第 10 周末）

- P0 缺陷清零，P1 有明确接受人和规避方案；
- 安全、隐私、性能、回滚和运营演练通过；
- 指标与业务事实抽样对账一致。

## 5. 测试方案

### 5.1 测试层级

- 单元测试：状态迁移、权限策略、价格/容量、脱敏、指标口径纯逻辑。
- 集成测试：数据库约束、Redis 锁、Outbox、对象存储、审核和通知适配器。
- API 契约测试：小程序/后台 DTO、错误码、分页、版本冲突、幂等。
- 端到端测试：首次入驻、发帖审核、邀约、评估支付服务退款。
- 手工探索：弱网、拒绝授权、多犬切换、跨社区、通知深链、小程序前后台切换。

### 5.2 必测风险场景

| 领域 | 场景 |
|---|---|
| 权限 | 猜测 ID、跨主人/社区/门店访问、过期授权、员工离职 |
| 位置 | 响应/日志/分享/缓存泄露精确坐标、关闭附近可见 |
| 内容 | 图片替换、二维码/联系方式、审核竞态、下架后缓存 |
| 邀约 | 最后名额并发、重复报名、活动中拉黑、临时取消、争议完成 |
| 容量 | 多人同时锁最后容量、支付超时释放、降容量 |
| 支付 | 重复回调、回调乱序、前端伪造成功、退款失败、对账差异 |
| 敏感数据 | 签名 URL 转发、后台导出、日志脱敏、注销后恢复 |
| 通知 | 重复、丢失、深链资源已删除、用户未授权订阅消息 |

### 5.3 非功能目标

- 以灰度预估峰值 5 倍做接口压测；
- 核心接口与任务做故障注入：数据库短暂失败、队列积压、微信超时；
- 依赖漏洞、静态扫描、密钥扫描和基础渗透测试；
- 备份恢复演练验证 RPO/RTO。MVP 建议 RPO ≤ 15 分钟、RTO ≤ 2 小时，待成本确认。

## 6. 灰度方案

### 6.1 分层放量

1. 内部账号：员工与测试狗狗，验证生产配置，不使用真实敏感资料。
2. 可信种子用户：5～10 名社区主理人，运营全程陪跑。
3. 小范围邀请：20～30 名核心犬主，开启内容与邀约。
4. 社区灰度：50～100 份真实狗狗档案，开启幼儿园真实订单。
5. 单社区开放：只在安全、成行、留存与服务质量稳定后进行。

每层至少观察一个完整核心周期；涉及幼儿园时至少完成数笔从评估到接回的真实订单。

### 6.2 灰度控制

- 功能开关按用户、社区、门店和版本控制；
- 幼儿园支付、邀约发布和定位能力可独立关闭；
- 写路径新旧版本兼容，旧客户端遇到不支持状态时提示升级；
- 运营每天复盘内容、邀约、订单、举报和异常，不用只看注册量。

### 6.3 暂停放量条件

- 发现精确位置、健康凭证或联系方式越权泄露；
- 重复扣款、容量超卖、订单状态无法恢复；
- 严重安全事件未按 SLA 响应；
- 举报/审核积压持续超阈值；
- 核心链路错误率或崩溃率显著超过基线；
- 运营人力无法覆盖当前用户量。

## 7. 上线清单

### 产品与业务

- P0 验收签字；待确认问题有结论和责任人；
- 服务价格、容量、评估、取消退款、客服和异常 SOP 已配置；
- 种子内容已授权，运营排班和值班通讯录有效。

### 合规与安全

- 主体、备案、用户协议、隐私政策、未成年人和支付合规审查完成；
- 权限矩阵、数据清单、保存周期、注销与授权撤回验证；
- 高风险漏洞关闭，审计、告警与证据保全可用。

### 工程

- RC 固定、数据库迁移审查、备份完成；
- 微信配置、域名、证书、支付回调、模板消息生产验证；
- 仪表盘、告警、值班、Runbook 和状态页准备；
- 回滚包、降级开关和恢复演练通过。

### 数据

- 生产埋点 schema 已登记；
- 测试/员工账号排除；
- 首日漏斗、支付、订单和安全看板可用；
- 对账任务和数据质量告警启用。

## 8. 发布步骤

1. 发布向前兼容的数据库变更；
2. 发布后端与 Worker，保持新功能开关关闭；
3. 运行冒烟和权限探测，观察错误率、队列与数据库；
4. 提交/发布小程序版本，先对内部和种子用户开启；
5. 按灰度层级开启社区、邀约、支付等独立开关；
6. 每次放量记录版本、范围、指标基线、负责人和回退点。

避免周末、法定假日前或幼儿园无人值守时开启关键新能力。

## 9. 回滚与降级

### 9.1 原则

- 优先关闭功能开关或停止放量，其次回滚应用；数据库采用前向修复，避免破坏性降级。
- 支付与订单事实不可因应用回滚而丢失；回滚后继续消费并对账。
- 安全事件先阻断访问和保全证据，再恢复功能。

### 9.2 场景预案

| 故障 | 立即动作 | 恢复 |
|---|---|---|
| 登录异常 | 保持静态说明，关闭新注册 | 修复配置/回滚鉴权服务 |
| 内容审核不可用 | 新内容进入待审核且不可公开 | 重放审核队列 |
| 附近泄露风险 | 关闭附近与定位写入，清 CDN/缓存 | 修复、审计访问、评估通知 |
| 邀约异常 | 禁止新建/报名，保留已确认活动只读与取消通道 | 修复状态并逐单核验 |
| 支付异常 | 关闭支付入口，不擅自改已支付订单 | 渠道查单、回调重放、人工对账 |
| 容量超卖 | 关闭受影响日期服务，冻结新单 | 按支付时间与业务规则人工协调 |
| 日报/附件泄露 | 撤销签名 URL、禁用分享、保全日志 | 轮换密钥、修复鉴权、事件处置 |
| 数据库故障 | 切只读/维护页，停止非幂等 Worker | 按备份与日志恢复并核对 RPO |

### 9.3 回滚验证

- 登录、狗狗档案、通知和既有订单可读；
- 不产生重复支付、退款、报名或通知；
- 队列水位恢复，失败消息可重放；
- 数据库迁移兼容旧应用；
- 核心指标和审计无明显断点。

## 10. 上线后 72 小时

- 前 4 小时持续观察，之后按小时检查核心链路；
- 每日对账支付、退款、容量、邀约完成和北极星构成；
- 所有用户反馈进入统一工单并关联版本、trace_id 和业务 ID；
- 24 小时和 72 小时分别做发布复盘，决定继续放量、保持或回退；
- 未经复盘不临时加入私信、商城等新范围。
